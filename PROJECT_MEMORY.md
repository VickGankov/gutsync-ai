## 2026-10-20 — Continue with Google
- Server-side OAuth code flow in `server/googleAuth.ts` (routes `/api/auth/google` and `/api/auth/google/callback`, registered in `server/_core/index.ts`), pure checks in `shared/googleAuth.ts`. Ends with the same session cookie as email login (`createSessionToken(user.id)`). State is a 10-minute httpOnly cookie compared in constant time; `next` must be a same-site path; the id_token (received directly from Google over TLS) is checked for issuer, audience, expiry and `email_verified`.
- Accounts: Google users are stored with `openId = google:<sub>`, `loginMethod = google` (no migration). Sign-in with the same email as an existing password account LINKS it and removes the password (email signup never verified the address, so a stranger could have registered it first); the person lands on `/profile?notice=google-linked` and sees a one-time toast. Password login for a Google account says to use Google; Forgot password still lets them add a password.
- The sign-in page shows the button only when `auth.providers` says Google is configured. Errors come back as `/auth?error=google_*` and show a message.
- Needs Render env: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `APP_BASE_URL` (must match the origin registered with Google). Redirect URI to register: `<APP_BASE_URL>/api/auth/google/callback`. When the custom domain arrives: add its callback to the Google client, change `APP_BASE_URL`; users get signed out once because the cookie belongs to the domain. Consent screen must be published before non-test users can sign in. `GOOGLE_AUTH_URL`/`GOOGLE_TOKEN_URL` exist only so tests can point at a fake Google.
- Tested end to end against a fake Google (new user, returning user, linking, cancel, bad state, unverified email, wrong audience, redirect safety); the real Google handshake and iPhone Home Screen app are untested. Apple sign-in would be required if a native iOS app is ever shipped with Google sign-in.
- Local only until the owner approves a push.
